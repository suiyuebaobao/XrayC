XrayC 整體優化與開源專案對比建議
查核日期：2026-10-05（台灣時間）
性質：分析與候選方案，尚未實作或取代既有開發方案。

結論
建議保留 Rust / PostgreSQL / Vue / Xray / access-agent 架構，優先把 XrayC 做成可靠的多節點中轉與流量營運平台。最有價值的一輪更新，是統一線路資料來源、分離歷史帳務與可刪除設定、降低無變更時的同步成本，再改善部署與使用者介面。
目前沒有證據需要整套重寫、立即拆微服務或更換資料庫。也不能因為使用 Rust 就宣稱比其他面板更快。

評估範圍與界線
閱讀了架構與開發方案、七個 Rust crate 的主要職責與關鍵流程、API/Agent/Worker、配置與授權模型、流量入帳與保留策略、安裝任務、訂阅和前端流程、備份及發布腳本。
正式站僅查閱設定、日誌與 PostgreSQL 統計。本輪未修改正式站、日誌、保留策略、程式或資料；未重跑整套測試，也未做效能壓測。
本機程式與兩套部署不可混為同一版本：先前新增的無限流量支援在新環境驗證過，不代表舊正式站已發布同一版本。
競品比較依官方文件、正式 release 與部分固定版本源碼；沒有同硬體、同工作量的比較壓測。版本數字、功能數量與 GitHub 熱度不等於穩定性或效能。

一、目前值得保留的設計
1. 入口、出口、綁定、分組、套餐授權分工清楚；使用者訂閱隱藏出口憑證。
2. 流量採累計計數器差值入帳，已有交易保護、過期/重複上報處理，以及零增量不入帳的邏輯；不可因減少日誌而破壞這些機制。
3. Agent 已有配置版本/雜湊、應用回執、候選配置檢查、失敗回滾與本機配置快取；後續應強化這套流程，無須從零重做。
4. 使用者限速與套餐授權有明確模型；實際內核能力不足時，應準確標示功能降級。
5. 已有日/小時流量彙總、本機與異地備份、WAL/PITR、隔離資料庫測試和實機測試腳本。問題是覆蓋與整合品質，不是全部缺失。

二、已確認的問題與靜態風險
A. 已確認：帶歷史流量的節點刪除會遇到外鍵衝突。
正式站日誌顯示 DELETE FROM access_nodes 觸發 usage_daily_rollups_exit_endpoint_id_fkey。當次相關出口仍有 63 筆日彙總、892 筆小時彙總，失敗交易回滾。
刪除前 helper 明確處理 access_line_id，節點/出口關聯仍交由多級級聯處理。已定位到這一段；具體觸發順序仍應在隔離資料庫驗證，不能在正式站反覆刪除重現。

B. 已確認：一鍵安裝曾使用失效的中心地址，導致制品清單下載失敗。
該地址已按使用者要求修正。優化重點是讓系統在部署前檢查「節點實際使用的中心地址、鑑權與制品」，並把來源及結果顯示出來，防止設定漂移再次發生。

C. 已確認：安裝失敗資訊與進度顯示不可靠。
摘要只保留前 512 字元，真正末尾錯誤可能被截掉；完整錯誤仍可能保留於 result.error。未知失敗步驟追加到清單尾端時，前面的下載、啟動、登記等未完成步驟被標成 done。

D. 靜態可見的同步成本風險。
crates/db/src/store/agent.rs 的 heartbeat_json 每次呼叫 sync_assignments_for_active_users，再 load_store_data、編譯配置。前者逐一同步全部有效使用者，後者載入全域模型。配置沒有改變時仍做大量工作，節點/使用者增加後會放大成本。尚未量測實際延遲或 CPU 收益，不能給出改善百分比。

E. 靜態可見的故障耦合。
run_worker_maintenance 在同一交易中處理套餐到期、訂單/認證狀態、探測與多種歷史清理，最後才提交。任一後段清理失敗都可能回滾前段業務處理；備份亦由同一 Worker 主迴圈等待執行。

F. 配置模型有多份狀態。
access_entries/access_entry_exit_bindings 是產品主模型，但 access_lines、exit_pools、使用者分配快取仍參與多處查詢和授權。此前出口停用再啟用未恢復線路的現象，是需要用一致性回歸測試保護的例子。

G. 正式部署與版本管理不夠明確。
正式站 API/Worker 仍為 development 模式，映像使用 local 標籤。不能把切换一個環境變數等同完成正式化；需先確認 HTTPS、Cookie、密鑰、遷移與版本相容性，再分批切換。

三、關於「日誌太細」的建議
首先分清四件事：計費狀態、帳務流水、監控採樣、診斷事件。它們的保留方式不能用同一個開關控制。

現況：程式已定義 usage_ledgers 明細 + usage_hourly_rollups + usage_daily_rollups 三層；預設明細保留 14 天、每批 5,000 筆，Worker 運行資料預設保留 14 天。正式站沒有查到這兩項政策的顯式設定覆寫，Worker 環境也設定為 14 天。不是「目前所有明細都永久保留」。
觀察到的主要表已配置空間約為：出口探測 81.2 MiB、線路指標 49.6 MiB、詳細帳本 36.4 MiB、入口探測 33.6 MiB、節點指標 27.2 MiB、會話事件 19.8 MiB；日彙總約 0.55 MiB。這些包含索引及已配置空間，不能直接當成有效日誌量或認定膨脹。
目前是幾百 MB 量級，沒有充分理由立即引入時序資料庫或做大規模分庫。

建議分兩步：
第一步只改展示與新資料寫入方式，不刪舊紀錄。
- 首頁顯示今日/本月用量、扣費量、在線狀態和異常；詳細流水放到二級頁面，按需查詢與分頁。
- 正常重複探測保留最新狀態，另以時間桶記錄成功率、延遲最低/最高/平均值；故障與恢復另外保留事件。
- 對一般效能圖做分鐘→小時→日的分層彙總，不降低配額控制所需的計費採樣精度。
- 使用者、入口、出口名稱變更或刪除，不能改寫歷史帳務含義。

第二步提出可選保留方案，再另行確認：
- 計費最新快照、去重與重啟基準：作為必要狀態保留，不能當一般日誌刪除。
- 流量明細：先沿用既有 14 天，不把縮短保留期當第一個修復。
- 高頻監控：可候選保留 24–72 小時，較粗時間桶保留較久。
- 連線/IP 與診斷事件：依排錯需求選擇短期保留；完整診斷模式可臨時開啟並自動退出。
- 日/小時帳務彙總：依查帳需求保留，與節點退役解耦。
以上是候選策略，不是已套用設定。現有日誌不因本建議而清理。任何歸檔/清理上線前，必須驗證彙總前後每位使用者的實際與扣費總量一致。

四、建議的目標設計
1. 配置保留唯一主來源。
以入口、出口、綁定、授權為主資料；執行期 access_lines/exit_pools 是可重建結果，不讓多個管理流程分別維護相同狀態。資源變動在同一交易記錄受影響節點及配置修訂，後台只重建那些節點。

2. 心跳保持輕量。
已有 desired/applied hash 機制應繼續使用；配置未變時僅更新存活狀態與回覆必要任務，不全量同步所有使用者。訂閱依使用者授權版本生成，快取必須隨停用、配額耗盡和憑證輪替失效。
流量 API 已能一次接收多筆 snapshots，但 DB 目前逐筆處理交易；未來依量測結果做有界批次優化，保留每筆接受/拒絕、補送與去重語義。

3. 物件退役與歷史帳務分離。
介面的刪除先做受控退役：停止新分配、撤銷必要憑證、同步受影響節點，再從活動清單隱藏。歷史資料保留穩定 ID 與當時名稱；不能依賴刪除活躍配置時一路級聯處理所有歷史表。短期先修既有關聯解除順序，長期逐步採用穩定身分/軟刪除模型。

4. 部署成為可觀察、有明確階段的任務。
順序為地址/鑑權/平台預檢→取得並驗證必要制品→準備候選設定→啟動與就緒→登記與確認；不要在必要制品尚不可取得時先拆掉既有可用環境。
進度只由實際事件推進。失敗後保留完整脫敏錯誤及發生步驟；錯誤摘要取關鍵原因，不一律截取開頭。將長時間安裝工作從 API 生命週期分離，任務可明確標記中斷和安全重試；SSH 密碼仍不進一般業務資料庫。

5. 拆分維護工作的交易與排程。
套餐到期、帳務彙總、監控保留、探測調度、備份各自處理失敗和重試。沿用 PostgreSQL 即可先落地工作佇列、租約及冪等處理，不因追求架構完整就立即增加多套基礎設施。

6. 讓健康與地址語義貼近使用者。
分開顯示「Agent 在线、設定已套用、TCP/UDP 可達、協定握手、實際請求」。現有伺服器之間可通，並不證明手機網路能直連。
把實際監聽地址、對外公布地址、轉送依賴分開建模。經節點 1 轉送的節點 2/3 應在拓撲中可見，避免三條線路看起來獨立，實際共用單一故障點。

7. 發布與使用介面收斂。
顯示 API/Worker/Agent/Xray 的版本、來源修訂和相容性；使用明確版本映像、發布紀錄與遷移說明。現有測試/發布腳本要區分唯讀檢查和會改動部署的操作。
日常主流程簡化為節點→建立可用線路→加入分組→授權套餐。一般使用者只看可用線路、期限與用量；複雜出口與傳輸參數放在進階設定。
目前只輸出 Clash/Mihomo YAML 是明確產品邊界。若手機客戶端需求增加，再評估從同一授權模型產生其他格式，需同步修改既有方案並完成相容性測試。
支付預設停用，WeChat 僅有設定/路由而無對應 provider 實作，應明確標示未開通/未實作，避免界面讓人以為已可收款。

XrayC 的定位判斷：
這幾個專案都已支援多節點；XrayC 值得保留的方向，是把「入口與出口組合、綁定級憑證與路由、套餐分組倍率、接入節點統一計费/限速」整合成自己的營運流程。這不等於其他專案完全做不到類似用途，也不等於目前 XrayC 更成熟。
若需求只是普通多節點發訂閱，應把採用成熟面板作為真實選項；若中轉與出口管理、分組倍率是核心業務，逐步改善 XrayC 比直接搬家更能保留現有語義。現有使用者、憑證、流量和套餐不能假定可無損直接搬到另一個專案。

六、落地順序與驗收條件
第一批：可靠性修復。
- 歷史流量節點刪除、出口停用再啟用、部署預檢、錯誤摘要與進度、重啟狀態如實回報。
- 驗收：在隔離資料庫覆蓋有日/小時彙總、共用出口、批次刪除、併發彙總等案例；操作前後帳務總量一致；保留線路可用；失敗回滾可確認。

第二批：同步與資料分層。
- 無變更心跳不全域重算；將維護交易拆開；統一執行期物化資料重建；預設摘要式監控。
- 驗收：無配置變動時不改寫全體授權；使用者停用/配額耗盡/憑證輪替仍及時生效；彙總工作失敗不阻止套餐到期處理；保留既有日誌。
- 量測新增節點/使用者前後的 SQL 次數、心跳延遲、配置套用時間、每小時資料增量；目前不承諾任何百分比。

第三批：正式發布與營運体验。
- HTTPS/production 模式預檢、版本化映像、Agent 相容性、備份還原演練、發布回退、操作嚮導和手機訂閱體驗。
- 驗收：測試與正式環境清楚區隔；設定、資料庫及必要密鑰均能還原；發布失敗可回到已知可用版本；日誌有獨立保留位置，不隨容器移除丟失。
- 回退程式映像不等於資料庫可以任意降版，遷移必須另外設計相容性與還原路徑。

暫不優先的工作
增加大量未驗證協定、重寫後端語言、大改 UI 風格、立即引入多套佇列/時序資料庫，以及為了報表好看而直接刪除正式日誌，都不是這輪最優先的收益來源。
若未來表規模和量測結果確實需要，再評估 PostgreSQL 按時間分區。官方說明亦強調分區效益與表規模/存取模式有關，不是所有表預設都應分區：
https://www.postgresql.org/docs/16/ddl-partitioning.html
