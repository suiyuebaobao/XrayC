四、真實資料面與安全行為
1. 跨機與協定
五條初始跨機路徑均 HTTP 200、下載 1,048,576 bytes，包含 3 台獨立節點及主控入口。普通 VLESS 臨時路徑後來用於刪除撤銷測試並移除。
自建出口 SOCKS5、HTTP、VLESS Reality、Shadowsocks 均完成真實流量。
入口／傳輸包含普通 TCP、Reality TCP、普通 WebSocket、普通 gRPC、普通 XHTTP、Reality gRPC、Reality XHTTP、Shadowsocks 2022。
新增的五種傳輸各 HTTP 200、16,384 bytes；三種新增出口各 HTTP 200、65,536 bytes。
Xray 26.5.9 與原生 Mihomo v1.19.32 實測；Mihomo 完整產生設定語法檢查通過，XHTTP Reality、普通 gRPC、SS2022 各 HTTP 200、65,536 bytes。
量子加密 VLESS：原生 Xray 與原生 Mihomo 各 HTTP 200、65,536 bytes。
上述為特定實測組合通過，不代表所有入口×出口×傳輸排列皆測過。

2. UDP
node-1 → SS2022 node-3 → SOCKS node-2 → UDP echo node-3：8/8 封包成功。
主控直達 node-3 的 UDP 與由主控發起的代理 UDP 逾時；node-1、node-2 直達則成功。原因尚未定位，不能斷言供應商封鎖或產品缺陷。

3. 限速、配額與帳務
主控 Ubuntu 核心支援 connmark 的環境：設定下載 1,000,000 bps，2 MiB 實測 18.613930 秒、112,665 B/s（約 0.901 Mbps）；上傳 512,000 bps，1 MiB 實測 17.851220 秒、58,739 B/s（約 0.470 Mbps）。
真實流量耗盡配額後代理憑證被撤銷；恢復配額後可連線。
2 倍計費實際帳本：delta_total=65,746、billing_multiplier=2.000、billed_bytes=131,492，符合兩倍。
收尾：套餐恢復 2 GiB，倍率 1 倍，使用者啟用，個別上下行限速覆寫恢復 null。已消耗的真實測試流量保留為證據。
TCP+UDP 同時流量共享限速未完成定量測試，不能由單獨 TCP／UDP 通過推定。

4. 身分、訂閱及撤銷
匿名存取管理 API 回 401；普通使用者回 403。
算術驗證碼錯答拒絕，正確新題可登入；註冊與邀請消耗通過。
登出清除本機登入狀態，refresh 回 401。
使用者與管理員訂閱 token 重設均有測試；最後一輪舊訂閱 HTTP 404、新訂閱 HTTP 200，舊代理憑證失效、新憑證可連線。
稽核抽樣 200 筆字串欄位，未發現提供的 SSH 密碼、Agent token、現行訂閱 token；這是抽樣結果，不是完整資訊安全審計。

5. 備份與還原
本機排程／手动 pg_dump 成功；備份還原到獨立資料庫，當時包含 47 張表、2 位使用者、3 個套餐。
異地 SSH 自動配置及備份傳送至 node-3 成功，offsite_synced=true；最後將全量目的地恢復 local。
WAL base backup 成功；實際建立 PostgreSQL named restore point，寫入 before/after 標記，在隔離複本恢復到 before，主庫維持 after；恢復複本完成 promote，標記與複本已清除。
此為隔離還原驗證，沒有破壞性覆蓋現行主庫。
最後全量與 WAL 狀態均 success；WAL enabled/configured=true。

五、確認的問題與目前處置
A. 出口重新啟用未恢復線路（未修復產品程式）
出口停用後重新啟用，部分資料仍為 access_lines.enabled=false，即使 binding.enabled 與 endpoint.enabled 已為 true。造成訂閱缺少原有線路；等待同步仍未恢復。
已透過官方 PUT 重新儲存受影響綁定恢復測試環境。這是繞過方式，不是根治。後續應修正出口更新與執行期線路狀態同步。

B. 重啟任務成功狀態不代表真的重啟（未修復產品程式）
node-3 實際回報 reboot_status=success，但訊息為「重启自检通过;重启命令未配置,未实际重启」。
實際主機重啟未測；需要配置可執行命令，並避免把僅自檢通過視作已重啟。

C. AlmaLinux 核心缺少下載限速能力
三台 AlmaLinux 9.7、5.14.0-611.55.1.el9_7.x86_64 核心 CONFIG_NET_ACT_CONNMARK 未啟用，modprobe 無法載入；IFB 可用。
Agent 正確回報 kernel_connmark_available=false，下載限速會降級。Ubuntu 主控支援此功能，TCP 限速測試在主控完成。
節點已設定 XRAYC_KERNEL_UPGRADE_COMMAND= 空值，避免無效的自動升級嘗試；沒有宣稱替換核心或解決三台節點的下載限速。

D. 全新部署 WAL 設定缺口（本環境已手動補齊）
archive_mode 已開，但 wal.configured 未自動成為 true，執行請求未真正執行；PostgreSQL pg_hba 也缺少 Worker 網段複寫授權。
驗證 archive_mode/wal_level 後補 configured 與限制於 Compose 子網的 scram-sha-256 replication 規則，reload 後 WAL 與 PITR 成功。尚未把這些處置納入通用部署程式。

E. 主控 UDP 路徑問題
已隔離出主控直達 UDP 也失敗；節點來源可通。尚未定位根因，詳見第四節，不計入已修復項目。

• 主機真的重啟：未配置執行命令。
• TCP+UDP 同時共享限速、長時間穩定性、大流量壓測、高可用切換、完整 make check-real-release：未執行。
