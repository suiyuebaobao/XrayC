# 一键部署脚本设计

> 状态:已与用户讨论确认大方向。单脚本、目标机本地运行、菜单选角色;镜像走自建 registry(公开拉、无鉴权、HTTPS)。
> 前后端分离体现在部署:前端、后端可分别单独安装(公网互联)。
> 本特性补上项目当前缺失的"运维侧一键把平台/前端/后端/数据库/仓库立起来"的引导脚本。

## 目标

让任何人在一台目标机上跑一条命令/脚本,从菜单选 5 个角色之一即可把对应组件装好:

1. **一体机**(前端 + 后端 + Caddy,子选 本地库 / 远程库)
2. **仅前端**(Caddy + 前端,反代到后端公网地址)
3. **仅后端**(api + worker,对外暴露端口)
4. **仅数据库**(postgres)
5. **镜像仓库**(自建 registry,分发上面所有镜像)

> **node 节点不在 install.sh 范围**:接入节点仍走管理面板现有的一键 SSH 安装(`deploy-access-agent`),口径不变。

镜像统一从**你们自建的 registry** 拉取,不依赖 Docker Hub/ghcr 等公共仓库。

## 非目标(YAGNI)

- 不做 registry 拉取鉴权 / 多租户 / 配额(用户明确:公开拉、不设限,只为做个分发仓库)。
- 不做前后端"服务间"额外鉴权:前端只是静态文件 + Caddy 透明反代,真正鉴权是浏览器↔后端(见 §四),拆开也不引入前后端共享密钥。
- 不做私网/内网假设:**用户网络只有公网**,前后端拆分按公网互联设计。
- 不做从中心远程 SSH 编排多机(脚本只管本机;远程装 node 仍走面板现有一键)。
- 不做 k8s/helm/系统级 systemd 编排(沿用 docker compose)。
- 不做 Web 化安装向导(命令行菜单 + 非交互参数即可)。

## 一、形态与运行模型

- 入口 `install.sh`,**在目标机本地运行**:`./install.sh` 起交互菜单,或 `./install.sh --role frontend --domain panel.example.com --api-upstream http://1.2.3.4:8000 ...` 非交互(便于自动化/复装)。
- **脚本分发**:`install.sh` 与各 compose 模板也由 ⑤ 那台中心机的 Caddy 对外用 HTTPS 提供,真正做到"一条命令装":`curl -fsSL https://<中心域名>/install.sh | bash`。脚本与镜像都来自你们自己的中心机,不依赖外部托管。
- 启动自检:docker / docker compose 是否就绪(缺则安装或明确提示);`df -h`、基础连通。
- **端口/服务冲突闸(真机试验得来的硬教训)**:装前检测本角色要用的端口(80/443/5432/后端暴露端口/registry 端口)是否被占。被占时**先判占用者是谁**:① 本项目上一次安装(`xrayc-*` 容器)→ 走幂等"升级/覆盖"流程;② **陌生服务(如他人的 nginx/代理服务/别的业务)→ 立即中止并清晰报告,绝不自动停别人的服务**(端口冲突无法绕过时让用户换机或自行让路)。这条对应红线"绝不动系统服务",已在真机试验中由某台测试机的他人代理/订阅服务占用 80/443 验证必要性。
- **薄入口 + helper 分文件**:`install.sh` 只做参数装配、菜单、公共流程;每个角色实现拆到 `scripts/lib/install/<role>.sh`(沿用 `deploy-access-agent.sh` 既有风格)。单文件 ≤550 行硬上限。

## 二、角色菜单(5 个)

| 角色 | 起哪些容器 | 带 Caddy | 关键输入 |
|---|---|---|---|
| ① 一体机 | postgres(本地库时)+ api + worker + **caddy**(含前端) | ✅ | 面板域名、ACME邮箱;子选 本地库 / 远程 `DATABASE_URL` |
| ② 仅前端 | **caddy**(含前端) | ✅ | 面板域名、ACME邮箱、**后端公网地址:端口** |
| ③ 仅后端 | api + worker | ❌ | `DATABASE_URL`、**对外暴露端口** |
| ④ 仅数据库 | postgres | ❌ | DB密码、允许连入的IP/网段 |
| ⑤ 镜像仓库 | registry + **caddy**(仅为 HTTPS) | ✅ | registry 域名、ACME邮箱、存储目录 |

> **node 节点不在 install.sh 范围**:接入节点(xray-core + access-agent)仍走管理面板现有的一键 SSH 安装(`deploy-access-agent`),口径不变。

**Caddy 口径**:带 Caddy 的只有 **① 一体机 / ② 仅前端 / ⑤ 镜像仓库**(前者托管前端+反代,⑤ 给 registry 上 HTTPS)。**③ 仅后端 / ④ 仅数据库不带 Caddy**。

> 前端"含在 caddy 镜像里":`deploy/caddy/Dockerfile` 是多阶段构建,先 `npm run build` 出前端 dist,再打进 `caddy` 镜像 `/srv/xrayc/frontend`。所以 ①② 拉 caddy 镜像即自带前端,**无需单独"部署前端 dist"步骤**。

## 三、前后端拆分:网络与反代(公网模型)

- **单一公网入口 = 前端(面板)域名**。浏览器、节点 agent 都只连前端域名(https)。
- 前端的 Caddy 把 `/api/*`、`/sub/*`、`/health`、`/api/deploy/artifacts/*` **反代到后端公网地址:端口**;其余路径发前端 SPA(`try_files {path} /index.html`)。
- **前端 → 后端这一跳是服务器对服务器**,不经浏览器,因此无跨域;订阅地址、节点中心地址都用前端域名。
- 节点 agent 的"中心地址"= 前端域名(`/api/agent/*` 经前端 Caddy 反代到后端);后端公网端口只需对前端机可达即可。
- **唯一一处真实代码改动**:`deploy/caddy/Caddyfile` 把写死的 `reverse_proxy api:3000` 改成可配置 `reverse_proxy {$XRAYC_API_UPSTREAM:api:3000}` —— ① 一体机默认同机 `api:3000`,② 仅前端填后端公网地址。

## 四、鉴权模型(决定了拆分走法,必须遵守)

- **前端不向后端做服务鉴权**:前端=静态文件,Caddy=透明反代,把浏览器带的凭证原样转给后端。前后端之间无共享密钥。
- **鉴权 = 浏览器 ↔ 后端**:
  - Access Token:JWT,走 `Authorization: Bearer` 请求头(SPA 的 JS 带上),后端 `require_admin/require_user` 校验。
  - Refresh Token:`HttpOnly` Cookie(`responses.rs:212`:`HttpOnly; Path=/; SameSite=Lax`,**无 Domain=host-only**,`Secure` 由 `XRAYC_REFRESH_COOKIE_SECURE` env 控)。后端拿它对 PostgreSQL(Argon2 哈希)换新 access token。
  - 后端栈:用户表 + Argon2 + JWT,登录/刷新/退出全在后端。
- **为何必须"浏览器只连前端域名 + 前端同源反代到后端"**:refresh Cookie 是 host-only + `SameSite=Lax`,只认浏览器当前访问域名。走前端域名反代→Cookie/JWT 同源无缝;若让浏览器直连后端域名(跨域)→ Cookie 被 SameSite 挡 + 需 CORS 带凭证,会坏。**所以同源反代是鉴权决定的唯一正确走法。**
- **部署默认**:① 一体机 / ③ 仅后端的后端运行环境 `XRAYC_REFRESH_COOKIE_SECURE=true`(生产 HTTPS 下 Secure Cookie 才下发)。脚本默认置 true,并提示 http 调试时才关。后端还须设 `XRAYC_PUBLIC_BASE_URL=https://<面板域名>`(订阅/回调等对外链接以面板域名为准,拆分下尤其重要)。
- **节点 agent 另一套**:access-agent → `/api/agent/*` 用 `Authorization: Bearer <agent_token>`(SHA-256 哈希校验),节点↔后端,与前端无关。

## 五、镜像分发模型(自建 registry)

- **发版(你做)**:中心构建机 `make package-docker-artifacts` 构建 api/worker/caddy(caddy 含前端)镜像 → 打标 `registry.example.com/xrayc/<svc>:<版本>` → `docker push` 到 ⑤ registry。
- **安装(谁装谁拉)**:`install.sh` 内 `docker pull registry.example.com/xrayc/...`;**公开拉取,无需 `docker login`**。
- **第三方基础镜像也搬进自家 registry**:`postgres:16-alpine`、`registry:2`、caddy 基础镜像统一 re-tag + push。这样**客户装机只访问你们 registry、完全不依赖 Docker Hub**(应对国内/Docker Hub 被墙,避免拉 postgres 卡死)。
- **HTTPS 必需(非鉴权,是 Docker 硬要求)**:registry 走 HTTPS,客户端无需改 `daemon.json` insecure-registries 即可直接拉。⑤ 的 Caddy 给 registry 域名自动签 ACME 证书并反代到本机 registry 容器。
- **启动顺序(解鸡生蛋)**:你先用 ⑤ 把 registry 立起来(它本身仅你这台、仅一次从 Docker Hub 拉 `registry:2`)→ push 全部镜像(含 re-host 的基础镜像)→ 之后所有安装只认你们 registry。

## 六、各角色的配置输入 + 密钥

通用红线:密钥一律**本地生成**、写入 0600 权限 `.env`、被 `.gitignore`/`.dockerignore` 排除;不进 git/日志/截图/提交说明。敏感初值(管理员口令、DB 密码)装完**仅打印一次**提示用户保存。

- **① 一体机**:问面板域名、ACME 邮箱、registry 地址;**自动生成** DB 密码(本地库时)、JWT 密钥;**建初始真实管理员**(问账号口令或自动生成并打印一次)——不是 `seed_demo_data` 的 demo 账号;`XRAYC_REFRESH_COOKIE_SECURE=true`、`XRAYC_PUBLIC_BASE_URL=https://<面板域名>`;`XRAYC_API_UPSTREAM=api:3000`(同机)。子选远程库时改填 `DATABASE_URL` 并装前校验连通。Caddy 自动签面板证书;**迁移由 worker 启动时跑(`MIGRATIONS_DIR=migrations`,镜像内置迁移文件)**。
- **② 仅前端**:问面板域名、ACME 邮箱、registry 地址、**后端公网地址:端口**(写入 `XRAYC_API_UPSTREAM`);只拉 caddy 镜像;`REFRESH_COOKIE_SECURE` 由后端环境决定(此角色不跑后端)。
- **③ 仅后端**:问 `DATABASE_URL`(远程库)、**对外暴露端口**(api 映射到公网,如 `8000:3000`)、JWT 密钥(与前端无关,后端自持)、registry 地址;`XRAYC_REFRESH_COOKIE_SECURE=true`、`XRAYC_PUBLIC_BASE_URL=https://<面板域名>`、`API_BIND=0.0.0.0:3000`;建初始管理员(若首装);worker 启动跑迁移(`MIGRATIONS_DIR=migrations`)。api/worker 同用 `rust-app` 镜像,`command` 分别 `xrayc-api`/`xrayc-worker`。
- **④ 仅DB**:自动生成或指定 DB 密码;问允许连入的后端机 IP/网段(写 `pg_hba.conf` + 暴露端口 + 防火墙提示);装完打印 `DATABASE_URL` 模板给 ①(远程)/③ 用。
- **⑤ registry**:registry 域名、ACME 邮箱、镜像存储目录(数据卷)。无鉴权。

## 七、幂等 + 升级

- **重跑安全**:检测到该角色已装,提示"升级 / 覆盖重装 / 取消";覆盖重装前明确二次确认,**不动数据卷**(postgres 数据、registry 存储、节点运行态保留)。
- **升级** = 重新 `docker pull` 新版本 tag + `docker compose up -d`;后端/一体机升级时 api 启动自动跑迁移;升级后复用 `check-running-images-current.sh` 校验运行的是新镜像(杜绝旧 image id 残留)。

## 八、健康检查 + 收尾

装完按角色自检,失败给清晰中文原因 + 回滚/排查提示:
- 一体机(①):容器 healthy、镜像新鲜、面板 HTTPS 可访问、登录 API smoke、DB 连通。
- 仅前端(②):caddy healthy、面板 HTTPS 可开、**反代到后端的 `/health` 通**(验证 `XRAYC_API_UPSTREAM` 配对)。
- 仅后端(③):api/worker healthy、暴露端口从外部可达、DB 连通、`/health` 与登录 smoke。
- 仅DB(④):postgres healthy、从指定网段可连。
- registry(⑤):registry HTTPS 可访问、`docker pull` 自家镜像可成功(探针镜像验证)。

## 九、测试

- **隔离 compose 验证**:各角色用隔离 docker compose 起一套(沿用 `compose-check` 思路),不复用既有 `127.0.0.1:8080` 服务。
- **真机(低配测试机即可,2核2G 够用)**:镜像在中心构建机(现有控制面机,算力足)构建 + push,**测试机只拉镜像 + 跑容器**(轻活,2G 够)。低配机即一次真实"低端客户机"footprint 验证。
  - **registry(⑤)放中心构建机**(本即"你们的中心仓库"),2核2G 测试机专测客户侧角色,既省内存又贴近真实拓扑。
  - **角色顺序测、测完拆**(2G 不一次堆全部容器):① 一体机本地库 → 拆 → ④ 仅DB + ③ 仅后端连该库 + ② 仅前端反代到该后端(验证前后端拆分 + 鉴权:真登录拿 JWT、刷新 Cookie 通)。每步真实拉镜像、真实起、真实回连闭环、真实迁移。
  - **前后端拆分要重点验鉴权**:浏览器(或 curl 模拟)只连前端域名,登录 → 拿 access token + 收到 HttpOnly refresh Cookie → 带 token 调 `/api/admin/*` 通 → refresh 换新 token 通。证明同源反代下 JWT/Cookie 无缝。
  - 更真的多机场景再拉现有私有清单服务器配合。
- **测试前置**:registry、面板需 HTTPS → 需子域名(如 `registry.<域名>` / `panel.<域名>`)DNS 指向相应机器(用户控制域名);临时可退用纯 HTTP + insecure-registry 跑通,但正式验证走真 HTTPS。
- **防泄露**:`.env`/token/密码/真实域名 IP 不进 git/日志/报告;脱敏代称记录"已覆盖 N 个角色"。

## 文件结构(实现时细化)

- `install.sh` —— 薄入口:参数/菜单/公共自检/分发到角色 helper。
- `scripts/lib/install/common.sh` —— 公共:docker 检测、密钥生成、`.env` 写入、registry 拉取、健康检查、日志。
- `scripts/lib/install/aio.sh` —— ① 一体机(本地/远程库按参数分支)。
- `scripts/lib/install/frontend.sh` —— ② 仅前端(caddy + `XRAYC_API_UPSTREAM`)。
- `scripts/lib/install/backend.sh` —— ③ 仅后端(api + worker + 暴露端口)。
- `scripts/lib/install/database.sh` —— ④ 仅数据库。
- `scripts/lib/install/registry.sh` —— ⑤ 镜像仓库。
- compose 模板:一体机 / 仅前端 / 仅后端 / 库 / registry 各自的 compose(或参数化现有 `docker-compose.yml`),放 `deploy/`。
- `deploy/caddy/Caddyfile`:`reverse_proxy` 目标参数化为 `{$XRAYC_API_UPSTREAM:api:3000}`(本特性需改)。

## 真机试验结论(2026-06-24,已验证)

在测试机(私有清单)中的干净机 + 本机中心上真机跑通(其中一台因有用户自有他人业务而全程不碰):

- **自建 registry**(…69):registry:2 + Caddy 自动 LE 证书(tls-alpn-01),`/v2/` HTTP/2 200;中心机 `docker push` rust-app/caddy/postgres 三镜像入库;远程机公开 `docker pull` 成功(无鉴权)。**免墙模型成立**(postgres 从自家仓库拉)。
- **DB 跨机公网拆分**:后端(…132)经公网连 DB(…69:5432),worker 启动跑迁移 **86 个全 applied、46 张表**。
- **前后端公网拆分 + 鉴权穿透(命脉,已独立复核)**:浏览器/客户端只连面板域名(前端 …123,HTTPS),Caddy 把 `/api`·`/sub`·`/health` 反代到后端(…132:8000)。实测:`/health` 200、SPA 200、`POST /api/auth/login` 200 拿到 `access_token` + `Set-Cookie: refresh_token HttpOnly; Secure; SameSite=Lax`、带 token `GET /api/admin/users` 200、不带 token 401。**JWT 头 + HttpOnly+Secure Cookie 跨公网拆分无缝穿透,印证 §四。**

### 试验得到的硬口径(必须固化进 install.sh)

1. **`XRAYC_ENV=production` 与 demo 种子互斥 + 强制 JWT 过期项**:源码 `crates/api/src/main.rs:117-119` 在 production 下**拒绝 `SEED_DEMO_DATA != false`**,且 production 强制要求 `JWT_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN`。故生产安装口径 = `XRAYC_ENV=production` + `SEED_DEMO_DATA=false` + 显式 `JWT_EXPIRES_IN`(如 15m)/`JWT_REFRESH_EXPIRES_IN`(如 7d)。`XRAYC_REFRESH_COOKIE_SECURE`/`JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` 独立读 env、不受 mode 影响(`state.rs:69-78`)。
2. **初始管理员 + 默认套餐 bootstrap(生产无法用 demo 种子,已实现)**:production 禁 demo 种子,故 api 启动改用幂等 bootstrap:① `bootstrap_admin` 按 `XRAYC_BOOTSTRAP_ADMIN_PASSWORD` env 建账号 `admin`(随机密码、真 Argon2、装完打印一次);② `bootstrap_default_plan` 在不播 demo 时建「基础套餐」(否则用户注册依赖默认套餐 + worker maintenance 报 `DefaultPlanNotFound`)。两者均无管理员/无默认套餐才建、幂等可重跑。已真机从零验收:装完 `admin` 经面板登录 200。
3. **Caddyfile 全局块换行**:`{ admin off }` 写一行会被 adapter 报 "no matching opening brace";全局选项块的 `admin off` 必须独占一行。
4. **2G 低配机余量偏紧**:3 容器栈(或 registry+DB 共存)装完各约 90MB free / 1.4G available,够用但后续加真链路联调要留意。

## 待定 / 实现期确认

- 平台/后端升级的 DB 迁移触发方式:api 启动自动 migrate(现状)还是脚本显式触发——实现时与现有 migrate 路径对齐。
- **node 节点不在 install.sh 范围**:接入节点仍走管理面板现有的一键 SSH 安装(`deploy-access-agent`),其镜像来源/装机口径维持现状,本脚本不涉及。
- registry 存储后端:本地文件卷(MVP)即可;对象存储为后续。
- ③ 仅后端是否需要给后端公网端口加最简 TLS(后端自带域名+证书)留作可选项;按用户"公网即可、不考虑风险"默认走明文公网端口,前端→后端服务器对服务器跳。
- 非交互参数全集与交互菜单字段一一对应,实现时定 flag 命名。
