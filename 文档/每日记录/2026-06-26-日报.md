### BUG-E 回归(真 BUG,已修复 + 活体验证)

- **现象**:compose v2 的机器上,新装节点永不收敛(config_dirty 恒真、validate failed、443 不监听)。

- **修复**(commit:控制面侧):从 `agent_install_envs()` 删除该无条件注入,改由 agent `config.rs` 内置等价默认在运行时由 agent 自身 sh -c 展开(不经 compose 插值)。新增回归测试断言 install envs 与手动引导均不再 emit 该 key。

## 七、中转节点增删改查审计 + 3 个真 BUG 修复(用户报「删域名删不掉、设置会乱、A 节点域名跑到 B」)

> 用户报告:在中转节点里删域名/CF 域名删不掉、设置会乱、给 …132 设的域名跑到 …123。按 systematic-debugging 取证(真机库实测 + 双盲复现),并派两个独立审查 agent(后端 CRUD / 前端 CRUD)通审。脱敏:节点统一用 …132/…123 代称。

### BUG-H 删不掉域名(真 BUG,已修 + PG 回归测试 PASS)
- **根因**:`UpdateAccessNodeRequest.domains` 是 `#[serde(default)] Vec`,区分不了「请求没带该字段」与「带了空 `[]`」——两者都成空 vec,被 handler 一律当「本次不改域名表」。于是用户在 UI 把域名删光(列表变空)→ 前端发空 `domains[]` → 后端不改 → 域名赖在库里 → 重开编辑框又出现 =「删不掉」。`sync_primary_node_domains` 清空单字段也不删主行,叠加放大。
- **修复**(用户拍板「不用兼容,直接改掉,用新的」):`domains[]` 改为节点域名**唯一真值源**,一律以请求清单对账(空清单=删光全部未被入口/出口引用域名);`update_access_node` 在单字段被 move 前先 `merge_primary_domains_into` 算好 desired,保证 access_nodes 单字段与 node_domains 一致。新增 `test_pg_update_node_empty_domains_clears_last_domain`(红→绿)。

### BUG-I token-less CF 节点编辑后被写成 dns01(真 BUG,审查 agent 揪出,已修 + 测试 PASS)
- **根因**:`routing_nodes.rs` 的 `update_admin_access_node` 裸 SQL `cf_cert_mode = CASE WHEN 提供了cf_domain AND 非空 THEN 'dns01' ...`,**只看 cf_domain 有没有就无条件写 dns01,无视 acme**,与已修的 create/rebind 口径(`derived_cf_cert_mode`:有 cf_domain 且有 acme 才 dns01)分叉。入口 TLS 证书锚定就读这一列(`routing_entry_cert.rs`),dns01 会把 CF 入口证书锚到 cf_domain 的 DNS-01 路径——token-less 签不出 → TLS 起不来。这是此前「CF 就配成 CF、免 token」没修干净的残留(CF 修复只改了 create/rebind)。
- **修复**:CASE 改为按「本次生效后的 cf_domain + acme」派生,与 create/rebind/node_domains 完全一致(无 acme→reuse_direct、有 acme→dns01),并修「清空 cf_domain 残留 dns01 脏值」。新增 `test_pg_update_node_cf_cert_mode_derives_from_acme`(覆盖两分支)。

### BUG-J 前端域名行用数组下标当 :key,删行 UI 串位(真 BUG,前端审查 agent 揪出,已修)
- **根因**:`NodeDomainsField.vue` 的 `directRows/cfRows` 用**会随 splice 变化的全局数组下标 `item.index`** 当 `:key`(:68/:94)。删一行后下标整体前移,Vue 按位置复用输入框/单选实例 → 行内容与「主域名」选中态整体串位,正是用户感知的「删不掉、设置会乱」。
- **修复**:改用 WeakMap 按行对象身份分配稳定 key(splice 不变),自包含只改本组件。

### 「…132 域名跑到 …123」跨节点串台:前后端均确认**非 BUG**
- 后端:建俩 dummy 节点真机实测,给 A 加域名/CF 域名、连续编辑 B,A 的域名**始终只在 A**;审查 agent 逐路径确认所有 node_domains 写都按 `access_node_id` 隔离、读模型按主键挂载,无跨节点写。

### BUG-K CF 证书模式判据错误:acme 被误当 DNS-01 凭据信号(真 BUG,处理 server_4「旧问题」时揪出并修)
- **现象**:真实 CF 节点 server_4(只有 cf 域名 + 有 acme 邮箱)被判 `cf_cert_mode=dns01` → 入口证书锚到 cf_domain 的 DNS-01 路径,token-less 签不出 → 被 BUG-D 兜底跳过该 CF inbound,CF 实际不可用;且 `cf_enabled` 因装机早于 rebind-sync 修复而陈旧为 false。
- **根因**:控制面 4 个派生点(create/rebind 的 `derived_cf_cert_mode`、`sync_primary_node_domains` 的 cf 主行、update 的裸 SQL CASE、`routing_node_domains::derive_cf_cert_mode`)都用「有 cf_domain 且有 acme → dns01」。但 **acme 邮箱是直连证书 HTTP-01 也要用的同一邮箱、根本不是 DNS-01 凭据信号**(DNS-01 给 cf_domain 签证书需 CF API token,而 token 不持久化)——「有 acme→dns01」会把「有直连证书的 token-less CF 节点」一律误判 dns01。agent 侧本就默认 reuse_direct(`config.rs`「只有控制面显式注入 dns01 才走 DNS-01」),控制面却反着来。
- **修复**:控制面 4 个派生点全部改为**默认 reuse_direct(token-less 免 token)**,与 agent 默认、`routing_entry_cert` 锚定口径对齐;dns01 只在运维**显式**于 cf 域名上设 `cf_cert_mode='dns01'` 时才落(经 `add_node_domain`→`derive_cf_cert_mode` 保留显式覆盖)。这才是「CF 就是 CF、免 token」的正路。
- **测试**:派生类测试(part47/part51/part56/part66 + api `test_pg_update_node_cf_cert_mode_defaults_reuse_direct`)断言改 reuse_direct;dns01 锚定/心跳类测试(part53/part58)改为**显式置 dns01** 以保留 dns01 路径覆盖。
- **server_4 收尾**:重建后重存 server_4 → `cf_enabled` 转 true、`cf_cert_mode` 转 reuse_direct(token-less)。注:真要跑 CF 流量,reuse_direct 需源站有一张有效直连证书(BUG-D:无则跳过该 inbound),server_4 目前只有 cf 域名、暂无入口,模型已正确,后续建 CF 入口要跑流量时需补直连证书域名。
