## 1. 设计(brainstorm → spec)

- **形态**:单脚本 `install.sh`,**在目标机本地跑**——`./install.sh` 起交互菜单,或 `--role <角色> --domain ... --api-upstream ...` 非交互(便于自动化/复装)。薄入口只做参数装配/菜单/公共自检/分发;每角色实现拆 `scripts/lib/install/<role>.sh`(沿用 `deploy-access-agent.sh` 风格)。单文件 ≤550 行硬上限。
- **6 角色菜单**:① 一体机(前端+后端+Caddy,子选本地库/远程库)② 仅前端(Caddy+前端,反代到后端公网地址)③ 仅后端(api+worker,对外暴露端口)④ 仅数据库(postgres)⑤ node 节点(xray+access-agent,复用 `deploy-access-agent.sh`)⑥ 镜像仓库(自建 registry)。带 Caddy 的只有 ①②⑥。
- **镜像走自建 registry**:统一 `docker pull <registry>/xrayc/<svc>`,**公开拉、无鉴权、HTTPS**(HTTPS 是 Docker 硬要求,非鉴权——⑥ 的 Caddy 给 registry 域名自动签 ACME 证书)。**第三方基础镜像也搬进自家仓库**(`postgres:16-alpine`、`registry:2`、caddy 基础镜像 re-tag + push),客户装机只访问你们 registry、完全不依赖 Docker Hub(免墙,避免拉 postgres 卡死)。
- **前后端分离部署**:单一公网入口 = 前端(面板)域名;浏览器、节点 agent 都只连前端域名;前端 Caddy 把 `/api/*` `/sub/*` `/health` `/api/deploy/artifacts/*` 反代到**后端公网地址:端口**,其余发前端 SPA。**唯一真实代码改动**:`deploy/caddy/Caddyfile` 把写死的 `reverse_proxy api:3000` 改成可配置 `{$XRAYC_API_UPSTREAM:api:3000}`。
- **自带账号**:装完自建初始真实管理员 `admin`(随机密码,**仅打印一次**)——**不是 `seed_demo_data` 的 demo 账号**。
- **非目标(YAGNI)**:不做 registry 拉取鉴权/多租户/配额、不做前后端服务间额外鉴权、不假设私网(用户网络只有公网)、不做远程 SSH 编排多机、不做 k8s/helm、不做 Web 安装向导。

## 2. 鉴权口径确认(决定了拆分的唯一正确走法)

- **前端不向后端做服务鉴权**:前端=静态文件,Caddy=透明反代,把浏览器带的凭证原样转给后端,前后端之间无共享密钥。
- **鉴权 = 浏览器 ↔ 后端**:Access Token 走 `Authorization: Bearer` JWT 头(SPA 的 JS 带上);Refresh Token 走 `HttpOnly` Cookie(`responses.rs:212`:`HttpOnly; Path=/; SameSite=Lax`,**无 Domain=host-only**,`Secure` 由 `XRAYC_REFRESH_COOKIE_SECURE` 控)。后端用它对 PostgreSQL(Argon2 哈希)换新 access token。
- **为何必须同源反代**:refresh Cookie 是 **host-only + `SameSite=Lax`**,只认浏览器当前访问域名。走前端域名反代 → Cookie/JWT 同源无缝;若让浏览器直连后端域名(跨域)→ Cookie 被 SameSite 挡 + 需 CORS 带凭证会坏。**所以「前端反代到后端」是鉴权决定的唯一正确走法。**

## 4. 试验得到的硬口径(已固化进实现)

1. **production 禁 demo 种子 + 强制 JWT 过期项**:源码 `crates/api/src/main.rs:117-119` 在 production 下拒绝 `SEED_DEMO_DATA != false`,且强制要求 `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN`。故生产安装口径 = `XRAYC_ENV=production` + `SEED_DEMO_DATA=false` + 显式 `JWT_EXPIRES_IN`(15m)/`JWT_REFRESH_EXPIRES_IN`(7d)。
2. **初始管理员 bootstrap 是关键缺口**:production 既禁 demo 种子,install.sh 必须有另一条建首个真实管理员的路径,否则装完无法登录后台 → 见 §5 实现。

4. **2G 低配机余量偏紧**:3 容器栈(或 registry+DB 共存)装完各约 90MB free / 1.4G available,够用但后续加真链路联调要留意。

## 11. 自测抓出真 bug:install.sh Caddyfile 上游默认值语法(`:-` → `:`)

真机自测(重建 caddy 含新前端)时,面板 SPA 200 但 `/health`、`/api/auth/login` 全 **502**,且**控制面上真实节点的 agent 心跳/上报也在 502**——这次 rebuild 把活的控制面 /api 代理打挂了。按系统调试取证:caddy 日志 `dial tcp: lookup -api: no such host`——反代去连了主机 `-api`。

- **根因**:b01164b 把 `deploy/caddy/Caddyfile` 参数化成 `{$XRAYC_API_UPSTREAM:-api:3000}`,用了 **bash 的 `:-` 默认值语法,但 Caddy 的环境变量默认值是单冒号 `{$VAR:default}`**。未设 `XRAYC_API_UPSTREAM` 时,Caddy 把"第一个冒号之后"整段当默认值 → 默认值成了 `-api:3000` → 去连主机 `-api`。佐证:同文件第 5 行 `{$CADDY_SITE_ADDRESS::80}` 正是单冒号默认值(默认 `:80`)。install 真机测试当时 env 被显式设上才没踩到;dev compose / aio 默认依赖这个默认值,才在自测时暴露。
- **修复**:`deploy/caddy/Caddyfile` 4 处 `{$XRAYC_API_UPSTREAM:-api:3000}` → `{$XRAYC_API_UPSTREAM:api:3000}`;文档里被照抄的 14 处坏语法(AGENTS/CLAUDE/开发方案/总口径/spec/实现计划/本日报 §1·§5)一并改正,grep 归零。
- **即时恢复**:`admin off` 关了 caddy admin API 无法热 reload → `docker cp` 修复版 Caddyfile 进容器 + `docker restart xrayc-caddy-1` 重读 → /health 200、login 200、SPA 200,真实 agent 心跳恢复;再 `docker compose up -d --build caddy` 把修复烤进镜像。
- **教训**:① Caddy env 默认值是 `:` 不是 bash 的 `:-`;② 参数化默认值必须在"不设该 env"的场景真机验过(install 测试设了 env 掩盖了 bug);③ 自测的价值——不自测这个 bug 会在客户 aio 一键装时直接爆。

## 12. 本机出口连接方式真 bug:默认预填线路没按节点能力过滤(我先误诊了)

用户复测说"本机出口服务里选 IP 直连还能看到 trojan/hy2"。我**先误诊**:只验了协议下拉的过滤(那个是对的),自测还专挑 domains=0 的 IP 节点测——那种节点 `lineDomainKind` 恒空、协议天然过滤,**根本没考验真正的链路**,所以假绿。用户两次说"明显不对",我才回到系统调试、把弹窗真实渲染截图看清。

### 20.2 抓到的真实问题(核心产出)

① **本地起的前端不能驱动一键安装(`controlPlaneUrl=window.location.origin`)**:一键安装从**本地 vite 前端**发起时,前端把 `controlPlaneUrl` 取成 `window.location.origin`(= `http://127.0.0.1:521x` / localhost),远端 agent 据此回拉安装制品时指向中心机 localhost、**拉不到制品 → 一键安装在远端失败**。**流B 证实**:改用**公网面板地址(脱敏的中心面板域名)**发起即解,远端可达制品、一键安装成功。结论:本地前端不能作一键安装驱动端,须用公网面板地址。

② **部署任务「progress report skipped」被误判失败 + 自伤式重装重试风暴**:流B 部署任务出现 `远程安装命令执行失败: [xrayc-access-deploy] deployment progress report skipped` 被标 failed,但**节点心跳实际正常上线**(`NODE_ONLINE=true`,`DEPLOY_TASK_STATUS=succeeded` 为最终态)。「进度上报被跳过」不应等同部署失败——见 failed 就强制重装会触发**自伤式重装重试风暴**(反复 SSH 重装同一节点)。**应以心跳判定部署成功**,而非以中途 progress report 是否到达判定。

③ **套餐授权分组首次未持久化致订阅 422(A2 复核/修复结论为准)**:首次跑 Phase A 时套餐授权分组写入缺失,用户订阅拉取 422(套餐未授权任何分组 → 无可输出入口)。A2 复核补绑授权分组后,**待出口端点探测从 offline 转 healthy,订阅即由 422 → 200**(`SUB_200_REACHED`,见 `poll-sub-200.out`);说明 422 同时受「授权分组缺失」与「绑定出口处于 offline 探测态」双重影响,补授权 + 出口 healthy 后订阅恢复 200。是否存在 UI 首次保存未落库的持久化 bug,以 A2 复核结论为准。

④ **本机出口 host 空回退到 CF 域名致探测失败(流B 已修)**:流B 本机出口创建时 host 留空,回退取到了 CF 域名,导致出口探测失败(本机出口本应连同机直连地址,不应落到 CF 域名)。**流B 修复**:删除错误本机出口,以 **IP host 重建** + 重新绑定 CF 入口,exitfix 测试通过(`real-op-phaseB-cf-exitfix.spec.ts` 1 passed),出口探测转 healthy、订阅 200。

⑤ **测试清单 server_3 与生产真实客户节点宿主机重叠**:清单里 server_3 宿主机与生产「美国高防中转」真实客户节点同机重叠。流C 因此**改用 server_2 顶替**(`PHASEC_TARGET_NOTE=server_2_substitute(server_3_is_real_customer_node_host)`)避开生产宿主机。**根因**:清单生成未排除生产 IP。

⑥ **【严重·订阅 422 真根因】agent 限速器在 `act_connmark` 内核模块加载失败时整次配置 apply 永久失败**:A2 SSH 进真实节点 server_1 复现——节点 `config_dirty_reason = limiter command failed: tc filter ... action connmark action mirred ...`;`modprobe act_connmark` 在 **kernel 5.15.0-181** 返回 `Invalid argument` 无法加载,去掉 connmark 的同款 tc 命令 `rc=0`。后果:`limiter.rs` 基础限速计划**无条件下发** `matchall+connmark+mirred` 规则,连一条 tc 失败就整次 apply `bail` → agent 上报失败 → `store/agent.rs:record_config_result` 把 `desired_config_hash` 重置 NULL → **节点永不收敛、入口端口永不监听、出口探测永远 offline → 订阅永远 422 死循环**。这是订阅 422 的**真根因**(③ 的授权分组只是次要并发因素,`plan_line_groups` 经 A2 真实 UI 复核 0→1 持久化正常、**非 UI bug**)。A2 绕过:该测试套餐零限速,置 `XRAYC_RATE_LIMITER_ENABLED=false` 重建 access-agent 容器后节点立即收敛、4 入口端口 LISTEN、探测 healthy、**订阅 422→200**。此 bug 连着本场早先 `7ebab61` 恢复的 connmark 下行整形规则——整形语义正确。**【用户澄清·复核定性,重要】生产环境只部署新内核,`act_connmark` 正常加载、connmark 下行整形正常工作——此问题仅出现在本次那台旧内核(5.15.0-181)的测试 VPS(server_1),属测试环境产物,不是生产 bug。故不做任何代码改动**(一度起的"健壮性降级"修复已按此澄清整体还原,`limiter.rs` 保持 `7ebab61` 现状、新内核下行整形不变)。教训:这条"真根因"是测试机内核太旧造成的假性严重问题,生产不受影响。**【后续实测重大纠正】** 随后登录生产真实客户节点「美国高防中转」(server_3)核查,发现它**也在旧内核 `5.15.0-30`**——与"生产只有新内核"的假设不符!所以 ⑥ 其实是**被旧内核掩盖的潜在生产风险**(若先升 agent 不升内核,新 agent 的 connmark 规则会在旧内核 `act_connmark` 加载失败 → 把生产节点卡死)。已按"**内核先于 agent**"的安全顺序对该生产节点完成升级:**内核 `5.15.0-30` → `6.8.0-124`(act_connmark 现正常 `loadable`)、agent 升到含 7ebab61 的最新镜像**;升级后节点配置干净应用(`dirty=false`、无 limiter 报错)、客户服务全程无损(xray 容器未中断,仅内核重启断 ~50s、agent 换镜像控制连接断 ~20s)。**结论修正:⑥ 不是纯测试环境产物,而是真实潜在生产风险,现已通过升级生产节点内核+agent 实测闭环根除;限速器代码无需改(6.8 上 connmark 本就正常工作)。** 遗留:应核查是否还有其它仍在旧内核的节点。

**本轮新功能真实流量验证(头号目标)PASS**:经 IP直连普通VLESS 入口(20001,`transport=xudp`)真实 xray 客户端——**TCP 出网 PASS**(出网 IP=中转节点 IP,确认经中转)、**UDP/XUDP 出网 PASS**(SOCKS5 UDP-associate 走 XUDP 隧道 DNS 查询收到合法应答)、**计费 9MB 真实递增**(Xray Stats 快照差值)、**防泄露 PASS**(订阅不含出口 dest/端口/uuid/private_key);Reality(20002)、域名 TLS(20003)出网均 PASS;**剔除 PASS**(禁用用户→订阅 404→在线客户端被真实剔除 rc=35)。注:A2 的"恢复用户"收尾步因主 Agent 清理脚本已先抹除 e2e-realui 命名空间而未执行(主测试均在清理前完成,属轻微时序竞速,不影响验证结论)。
