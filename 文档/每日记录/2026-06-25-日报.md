## 3. 今日修复:悬挂 `binding_node_ids`(第 3 次测试抓到的真 bug)

### 现象
删除入口↔出口绑定相关链路后,分组 `line_group_binding_nodes` 残留指向「运行态线路已消失」的**悬挂 id** → 订阅 422「当前套餐没有可用线路」;且 UI 无干净移除路径(失效项仍透出但反选不掉),replace 接口又拒绝混入失效 id。

### 根因(已用真实隔离 PostgreSQL 核实,不靠假设)
- `access_lines.id` 与 `access_entry_exit_bindings.id` **同主键**(同步时 `al.id = b.id`);订阅/计费靠 `binding_node_ids.contains(&line.id)` 对 `access_lines` 判定可见(`crates/core/src/subscription.rs::access_line_belongs_to_group`)。
- DB 侧 FK `line_group_binding_nodes.entry_exit_binding_id → access_entry_exit_bindings(id) ON DELETE CASCADE` 在库里已确认是 CASCADE(`pg_constraint.confdeltype = 'c'`),正常删绑定 DB 会级联清行;**且该 FK 在 INSERT 侧也强约束**——无主绑定行无法直接插入。
- 真正的悬挂中间态:**绑定行 + `line_group_binding_nodes` 行仍在,但其运行态 `access_lines` 行已被清掉**(出口池剪枝 `prune_unusable_exit_pool_lines_in_tx`、出口/出口池删除等路径会删 `access_lines` 而保留 binding)。此时该 binding id 在订阅侧无对应可渲染线路 → 分组唯一线路全部不可见 → 整单 422;管理端读模型把该悬挂 id 透出后,前端反选卡在失效项上、replace 又拒它。

### 修复(最小改动、一处覆盖两端)
- `crates/db/src/store/load.rs` 的 `line_group_binding_nodes` 回填查询加 `WHERE EXISTS (SELECT 1 FROM access_lines al WHERE al.id = lgbn.entry_exit_binding_id)`,在**读模型源头**过滤掉缺运行态线路的悬挂 id。
- 管理端读模型(`access_routing_json`)与订阅/计费读模型(`load_store_data`)**同源**,故此一处过滤同时修复:① 订阅不再因悬挂 id 整单 422;② 管理端分组页不再透出失效项,前端反选/移除回归正常。防御性、幂等,connmark 可用路径行为零变化。

### 单测钉死(隔离 PostgreSQL 集成测试)
- 新增 `crates/db/src/tests/part42.rs::test_pg_line_group_binding_nodes_drop_dangling_after_binding_delete_when_database_url_is_set`:建节点/出口/入口/绑定 → 入组 → 删该 binding 的运行态 `access_lines`(保留绑定行 + 绑定节点行,复刻真实悬挂态)→ 断言管理端读模型与订阅读模型的 `binding_node_ids` 均不含该悬挂 id。
- 已实测:**去掉 `load.rs` 的 EXISTS 过滤该测试失败,加上则通过**(钉死回归)。
